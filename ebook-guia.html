1. O QUE É AUTOMAÇÃO ON-CHAIN (E O QUE ELA NÃO É)

Automação on-chain é a engenharia de fazer um computador executar
transações em blockchains de forma programática, repetível e
controlada — sem intervenção humana a cada passo.

Exemplos do que este guia ensina:

  • Um script que verifica saldos e executa swaps quando condições
    pré-definidas são atingidas
  • Um agendador (cron) que roda tarefas em horários fixos
  • Um ledger que registra cada transação com custo de gas
  • Rotação de RPCs para manter disponibilidade
  • Segurança de chaves privadas com criptografia local

O que automação NÃO é:

  • Não é "dinheiro automático" — o mercado pode cair e você pode
    perder capital em qualquer operação
  • Não é arbitragem garantida ou yield "sem risco" (risco zero não
    existe; impermanent loss, reentrância e rug pulls são reais)
  • Não é um robô que "nunca erra" — erros acontecem, e por isso
    este guia dedica um capítulo inteiro à depuração

A premissa deste material: você vai construir um sistema que
opera por você, mas vai entendê-lo por inteiro — porque no
momento em que uma transação falha ou um saldo some, é o
entendimento da arquitetura que resolve.

2. FUNDAMENTOS: EVM, LAYER 2, GAS E CARTEIRAS

2.1 EVM e cadeias compatíveis

A Ethereum Virtual Machine (EVM) é o "processador" que executa
contratos inteligentes. Cadeias como Base, Optimism, Arbitrum e
Scroll são EVM-compatíveis: o mesmo código Python (via web3.py)
funciona em todas, mudando apenas o RPC e o chain ID.

Rede Chain ID Token nativo Moeda de gas
Ethereum 1 ETH ETH
Base 8453 ETH ETH
Optimism 10 ETH ETH
Arbitrum 42161 ETH ETH
Scroll 534352 ETH ETH
BNB Smart Chain 56 BNB BNB

Usar L2s (Base, Optimism) reduz drasticamente o custo de gas —
na Base, em períodos de baixa atividade, transações custam
centavos de real, contra dezenas de reais na mainnet.

2.2 Gas: o combustível de toda operação

Toda transação paga gas = (gas usado) × (preço do gas). Três
conceitos:

  • gas_limit: teto que você define (ex: 250.000)
  • gas_price: preço por unidade (em gwei ou via EIP-1559:
    maxFeePerGas + maxPriorityFeePerGas)
  • gas_used: o quanto a execução realmente consumiu (retornado
    no receipt)

Regra de engenharia: sempre mantenha saldo reserva para gas.
O pior cenário operacional não é perder dinheiro — é ter saldo
preso num token sem ETH para pagar o gas de movê-lo.

2.3 Carteiras: conta, chave e endereço

Uma carteira EVM é: (endereço público, chave privada, frase
semente). Quem tem a chave privada controla os fundos.

Do ponto de vista de engenharia, sua carteira é um par de
cadeias: (address, private_key). Em Python:

from eth_account import Account

# NUNCA faça isso em produção com chave real — use variável de ambiente ou cofre
conta = Account.from_key(PRIVATE_KEY)
print(conta.address)  # 0x...

⚠️ A chave privada é o alvo. Ela não deve aparecer em código
versionado, logs, screenshots, chats ou backups na nuvem. O
capítulo 5 detalha como armazená-la.

3. ARQUITETURA DE UM SISTEMA DE AUTOMAÇÃO

Um sistema de automação on-chain saudável tem camadas bem
separadas. Pense como um pipeline:

┌─────────────────────────────────────────────────────┐
│ 1. FONTE DE DADOS   (RPCs, APIs de preço)           │
│       │                                             │
│ 2. CAMADA DE DECISÃO (regras: quando agir)          │
│       │                                             │
│ 3. CAMADA DE EXECUÇÃO (construir e assinar TX)      │
│       │                                             │
│ 4. CAMADA DE REGISTRO (ledger, logs, estado)        │
└─────────────────────────────────────────────────────┘

Princípios:

  1. Separação: decisão ≠ execução. A regra "comprar se preço
    < X" é lógica; o swap é efeito. Teste a decisão sem gastar gas.
  2. Idempotência: rodar o mesmo script 100 vezes não deve
    causar 100 transações. Cada ação deve ser registrada para
    não se repetir.
  3. Fail-safe: se algo der errado, o padrão é NÃO fazer nada
    (não "tentar mais agressivo"). Erro não é oportunidade.
  4. Reserva intocável: uma parcela do saldo nunca é usada em
    operações — é o "airbag" para gas e emergências.

5. SEGURANÇA DE CHAVES: O PILAR NÃO-NEGOCIÁVEL

5.1 O modelo de ameaça

Seu principal ativo não é o saldo — é a chave privada. Ameaças
comuns:

  • Chave em texto puro num arquivo de script (roubo trivial)
  • Chave enviada em chat/log (vazamento em logs)
  • Chave versionada no Git (roubo histórico: o commit fica pra
    sempre)
  • Phishing: sites que pedem sua frase semente ("claim", "verify")

5.2 Boa prática implementável em Python stdlib

Criptografia local com AES (usando cryptography):

from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.primitives import padding
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC
from cryptography.hazmat.primitives import hashes
import os, json

def cifrar_chave(chave_hex: str, passphrase: str, salt: bytes) -> bytes:
    kdf = PBKDF2HMAC(algorithm=hashes.SHA256(), length=32,
                     salt=salt, iterations=100_000)
    key = kdf.derive(passphrase.encode())
    iv = os.urandom(16)
    padder = padding.PKCS7(128).padder()
    dados = padder.update(chave_hex.encode()) + padder.finalize()
    cipher = Cipher(algorithms.AES(key), modes.CBC(iv)).encryptor()
    return salt + iv + cipher.update(dados) + cipher.finalize()

5.3 Regras operacionais de segurança

  • Permissões de arquivo: chmod 600 em arquivos de chave
    (evita leitura por outros usuários do sistema)
  • .gitignore: liste wallets/, *.enc, state/, logs/
    ANTES de criar o repositório... ou melhor, nem versionar
    a pasta de chaves
  • Sem segredos em logs: nunca print() chave; registre
    apenas endereço e hashes de transação (hashes são públicos
    e seguros)
  • Passphrase forte e nunca igual a senhas de e-mail
  • Conferir allowance: aprovar valor máximo (2^256-1) é
    conveniente mas amplia superfície; em contratos de terceiros,
    prefira aprovar apenas o necessário

6. CONECTANDO À REDE: RPCS, ROTAÇÃO E RATE LIMITS

6.1 O problema dos RPCs

RPC (Remote Procedure Call) é o endpoint que seu script usa para
falar com a blockchain. RPCs públicos são gratuitos mas frágeis:

  • Rate limit (HTTP 429: muitas requisições)
  • Bloqueio temporário (HTTP 403: "forbidden")
  • Queda total

Solução de engenharia: rotação.

RPCS = [
    'https://base.drpc.org',
    'https://1rpc.io/base',
    'https://mainnet.base.org',
    'https://base-rpc.publicnode.com',
]

def obter_w3():
    for rpc in RPCS:
        try:
            w3 = Web3(Web3.HTTPProvider(rpc, request_kwargs={'timeout': 30}))
            if w3.is_connected():
                return w3, rpc
        except Exception:
            continue
    raise RuntimeError('Nenhum RPC disponível')

Regra de ouro: a ordem importa. Endpoints estáveis (DRPC,
1RPC) primeiro; os que historicamente dão 403 (publicnode) por
último. Detectamos e corrigimos exatamente ese bug em produção:
o RPC "primeiro da lista" estava bloqueando (403) e derrubava
todas as leituras de saldo.

6.2 O padrão retry com backoff

import time, random

def enviar_com_retry(fn, tentativas=3):
    for i in range(tentativas):
        try:
            return fn()
        except Exception as e:
            if i == tentativas - 1:
                raise
            espera = 2 ** i + random.uniform(0, 1)
            print(f'tentativa {i+1} falhou ({e}); aguardando {espera:.1f}s')
            time.sleep(espera)

7. PRIMEIRA AUTOMAÇÃO: SWAP PROGRAMÁTICO ETH → TOKEN

Vamos montar um swap ETH → AERO na Aerodrome (Base) passo a
passo. O padrão serve para qualquer DEX com roteador
(router) V2/V3.

7.1 O fluxo de transações

  1. Wrap: ETH → WETH (token ERC-20 do ETH)
  2. Approve: autorizar o roteador a gastar seus WETH
  3. Swap: WETH → AERO (ou qualquer token)

O approve pode ser feito uma única vez com valor máximo
(aprove infinito) — depois, cada swap tem só 2 transações
(wrap + swap).

7.2 Código (essência)

import json, time
from web3 import Web3

WETH = Web3.to_checksum_address('0x4200000000000000000000000000000000000006')
AERO = Web3.to_checksum_address('0x940181a94A35A4569E4529A3CDfB74e38FD98631')
ROUTER = Web3.to_checksum_address('0xcF77a3Ba9A5CA399B7c97c74d54e5b1Beb874E43')

ABI_WETH_DEPOSIT = '[{"constant":false,"inputs":[],"name":"deposit","outputs":[],"payable":true,"stateMutability":"payable","type":"function"}]'
ABI_ERC20 = '[{"constant":false,"inputs":[{"name":"spender","type":"address"},{"name":"amount","type":"uint256"}],"name":"approve","outputs":[{"name":"","type":"bool"}],"type":"function"}]'

def wrap(w3, chave, valor_eth):
    nonce = w3.eth.get_transaction_count(Web3.to_checksum_address(conta))
    tx = w3.eth.contract(address=WETH, abi=json.loads(ABI_WETH_DEPOSIT)).functions.deposit().build_transaction({
        'from': conta, 'value': Web3.to_wei(valor_eth, 'ether'),
        'nonce': nonce, 'gas': 60000, 'chainId': 8453,
    })
    assinada = w3.eth.account.sign_transaction(tx, chave)
    return w3.eth.send_raw_transaction(assinada.raw_transaction)

7.3 Simulação antes de enviar (economiza gas)

Antes de assinar uma transação, use eth_call para simular —
custa zero e revela se a transação reverteria:

try:
    w3.eth.call({'from': conta, 'to': ROUTER, 'data': dados_do_swap})
    print('simulação OK — transação deve passar')
except Exception as e:
    print('REVERTERIA:', str(e)[:120])

Este padrão evitou, em produção, gas desperdiçado em pools sem
liquidez (erro execution reverted).

8. LÓGICA DE DECISÃO: RESERVAS, GATILHOS E LIMITES

O coração de qualquer automação é a função de decisão. Ela deve
ser determinística, conservadora e registrada.

def decidir_acao(saldo_eth, reserva, preco_atual, gatilho_compra, valor_max):
    """
    Retorna None (não agir) ou o valor (em ETH) a operar.
    """
    disponivel = saldo_eth - reserva        # 1. reserva intocável
    if disponivel <= 0:
        return None                          # sem folga, não mexe
    if preco_atual >= gatilho_compra:
        return None                          # 2. não compra caro
    valor = min(disponivel * 0.40, valor_max)  # 3. tamanho limitado
    return valor

As três regras de engenharia:

  1. Reserva intocável — nunca zera o saldo; o sistema precisa
    de gas para viver
  2. Gatilho anti-euforia — se o preço passou do limite, a
    resposta é NÃO AGIR (esperar), nunca "subir o limite"
  3. Tamanho máximo por operação — capital limitado por ação;
    nunca "all-in"

Importante: teste a decisão separadamente da execução.
decidir_acao(...) não custa gas; só quando ela retorna um
valor é que a execução acontece.

9. REALIZAÇÃO DE LUCRO: O PADRÃO TAKE-PROFIT (COMO ENGENHARIA)

Take-profit é um padrão de gestão de posição: vender uma fração
quando o preço sobe acima de um percentual sobre o custo médio.
No nível de engenharia, é um state machine com duas
variáveis persistentes: custo_medio e vendas_realizadas.

estado = {'custo_medio': 0.0, 'vendas': 0}

def verificar_take_profit(preco_atual, ganho_minimo=12.0, fracao_venda=0.15):
    if estado['custo_medio'] <= 0:
        estado['custo_medio'] = preco_atual   # primeira leitura = referência
        return None
    ganho = ((preco_atual / estado['custo_medio']) - 1) * 100
    if ganho >= ganho_minimo:
        return fracao_venda                     # vender fração
    return None

Armadilha clássica (vivida em produção)

O sistema ficou "travado" por semanas: o custo médio registrado
era de um período antigo (início da posição), e o gatilho de
+15% ficou a 22% de distância do preço atual. Correção:
recalibrar o custo médio para a média das operações recentes.
Lição: estados persistentes desatualizados cegam a decisão —
monitore custo_medio como se fosse um sensor.

Por que vender fração (ex: 15%) e não tudo

  • Mantém 85% da posição trabalhando (upside preservado)
  • Realiza caixa, que pode ser reinvestido (ciclo)
  • Reduz o impacto de erro de timing (mercado pode subir depois)

10. OPERAÇÃO 24/7: CRON JOBS, LOGS E IDEMPOTÊNCIA

10.1 Agendamento com cron

# crontab -e
*/30 * * * *  cd /caminho/projeto && .venv/bin/python scripts/verificador.py >> logs/verificador.log 2>&1
0 10 * * *    cd /caminho/projeto && .venv/bin/python agents/farmer.py >> logs/farmer.log 2>&1

10.2 Design de cada job (lições de produção)

Nossa grade tem ~15 jobs. O que aprendemos:

  1. Menor frequência possível para o objetivo — monitorar a
    cada 30min, farmar 1x/dia... não o contrário
  2. Cada job é autônomo e idempotente — se o PC desligou e o
    job roda "atrasado" em lote, ele não duplica transações
    (verifica estado antes de agir)
  3. Log para arquivo + stdout — diagnósticos sobrevivem a
    crash de terminal
  4. exit code significativo — 0 = ok/sem ação; != 0 = erro
    (permite alertas)
  5. Sem dependência de ordem — job A não espera job B
    (elimina cascata de falhas)

10.3 O caso real: PC desligado de madrugada

O notebook desligou; jobs noturnos não rodaram. Na volta, o
sistema executou tudo em lote. Como cada job é idempotente e
verifica saldos/reservas, os "atrasados" simplesmente avaliaram
as condições atuais e agiram se ainda fizesse sentido — sem
duplicação. Lição: idempotência não é luxo, é requisito de
sobrevivência.

11. OBSERVABILIDADE: LEDGER DE TRANSAÇÕES E MÉTRICAS

Você não pode operar o que não consegue medir. Um ledger de
transações registra cada operação: hash, bloco, horário,
função, custo de gas, status.

11.1 Estrutura mínima do ledger (SQLite)

CREATE TABLE transacoes (
    hash        TEXT PRIMARY KEY,
    chain       TEXT,
    bloco       INTEGER,
    ts          INTEGER,        -- timestamp
    de          TEXT,
    para        TEXT,
    valor_wei   INTEGER,
    gas_usado   INTEGER,
    gas_preco   INTEGER,
    taxa_eth    REAL,           -- gas_usado × gas_preco (em ETH)
    status      INTEGER,        -- 1 = sucesso, 0 = revert
    funcao      TEXT
);

+ eth_getTransactionReceipt. Varra os nonces da carteira:

Com o ledger, você responde perguntas que antes eram opinião:
"quanto gas gastei no total?" → query SQL. "Qual função custa
mais?" → GROUP BY funcao.

11.3 Métricas que importam

  • Taxa total de gas por semana (custo operacional real)
  • Tx bem-sucedidas vs revertidas (saúde do sistema)
  • Valor movimentado por ciclo (tamanho médio)
  • Saldo por chain (distribuição/risco)

12. MULTI-CHAIN: ARQUITETURA PARA CRESCER SEM QUEBRAR

Expandir para múltiplas chains (Base, Optimism, Arbitrum,
Scroll) é o mesmo código com configuração por rede:

CHAINS = {
    'base':     {'id': 8453,  'rpc': '...', 'weth': '0x...', 'router': '0x...'},
    'optimism': {'id': 10,    'rpc': '...', 'weth': '0x...', 'router': '0x...'},
    'arbitrum': {'id': 42161, 'rpc': '...', 'weth': '0x...', 'router': '0x...'},
}

Regras para multi-chain saudável:

  1. Reserva por chain — cada rede tem custo de gas diferente;
    configure reservas individuais (0.0005 na Base, 0.00005 em
    L2s baratas)
  2. Saldo mínimo para operar — chain com 0.000001 ETH não
    opera (não "força" transação por orgulho)
  3. Isolamento de falha — erro na Optimism não aborta a Base
    (try/except por chain)
  4. Fallback de DEX — se o pool A está sem liquidez, tente o
    pool B (ou não faça nada, se ambos falharem)

Lição de produção: o pool de VELO (Optimism) estava vazio
(sem liquidez) e o swap revertia. A simulação via eth_call
revelou antes de enviar. Trocamos o alvo para OP (líquido).
Sempre simule; nunca confie que "tem liquidez porque o endereço
existe".

13. DEPURAÇÃO: OS ERROS CLÁSSICOS E COMO RESOLVÊ-LOS

Erro Causa provável Solução
429 Too Many Requests Rate limit do RPC Rotação de RPCs + backoff
403 Forbidden RPC bloqueando o IP/chave Reordenar RPCs estáveis primeiro
execution reverted (no data) Pool sem liquidez / slippage Simular com eth_call antes
nonce too low Nonce desatualizado/cache Buscar nonce do node a cada envio
insufficient funds Saldo abaixo de gas+valor Verificar reserva antes de construir TX
Job "perdido" à noite PC desligado Idempotência + rodar em lote na volta
Take-profit nunca dispara Custo médio desatualizado Recalibrar estado

Protocolo de depuração (4 passos)

  1. Reproduzir — rode o script manualmente e capture o erro
  2. Isolar — é rede (RPC)? é contrato (revert)? é estado
    (nonce/custo médio)?
  3. Simular — eth_call para transações; teste unitário para
    decisões
  4. Corrigir com o menor delta — mude uma variável por vez;
    documente a correção (este guia nasceu dessas correções)

14. CHECKLIST FINAL E BOAS PRÁTICAS

Segurança

  • [ ] Chaves criptografadas localmente (AES + passphrase)
  • [ ] chmod 600 em arquivos de chave
  • [ ] .gitignore cobrindo wallets/, state/, logs/, *.enc
  • [ ] Nenhuma chave em logs, prints ou versionamento

Arquitetura

  • [ ] Camadas separadas: dados / decisão / execução / registro
  • [ ] Função de decisão testável (sem gas)
  • [ ] Reserva intocável por chain
  • [ ] Idempotência em todos os jobs
  • [ ] Simulação (eth_call) antes de toda transação nova

Operação

  • [ ] Cron jobs com log em arquivo e exit code significativo
  • [ ] Ledger SQLite alimentado por varredura de nonce
  • [ ] Rotação de RPCs (estáveis primeiro)
  • [ ] Backup da passphrase (papel, local seguro) — nunca na nuvem

Disciplina

  • [ ] Nunca "aumentar o risco" num erro (erro = parar, não forçar)
  • [ ] Nunca aprovar contratos não auditados por valor grande
  • [ ] Nunca enviar fundos para endereços não verificados
  • [ ] Documentar cada correção (a memória do sistema é o código
  • este guia)

Palavra final: automação on-chain é engenharia de verdade —
com as mesmas regras de qualquer sistema crítico: segurança
primeiro, decisões testáveis, operação observável e erros
documentados. O código deste guia é o esqueleto; sua disciplina
é o sistema nervoso.
